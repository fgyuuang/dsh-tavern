# DSH 酒馆：速度与调用复杂度的设计重构检查

日期：2026-10-15。检查对象：已有 `temp/latency-audit-20261015/assessment-and-redesign.md`
提出的重构，以及源码/部署中的实际落地状态。
本文件只做实测核对与设计检查，不修改运行策略以外的功能。

## 1. 一句话结论

**重构的方向是对的，代码也已经落地并部署，但它从未被真实回合验证过。**
现有唯一的耗时实测全部来自重构前的旧流程；因此「效果还是不理想」目前无法归因于新设计，
但同样也没有任何证据表明新设计已经变快。剩下的差距集中在三处：**回合内上下文无上限、
正文不出现在聊天、结算与附加仍各占独立请求**。

### 2.1 单次请求 20 万 token 由什么组成

turn 3 峰值请求（117 条消息，378,832 字符）：

| 组成 | 条数 | 字符 |
| --- | ---: | ---: |
| system（persona + 契约指令 + 协议） | 1 | 47,339 |
| user | 67 | 295,529 |
| assistant | 49 | 35,964 |

67 条 user 里，绝大多数是 **tool-result**，单条 20,287 / 22,213 / 25,873 / 27,151 /
28,229 / 28,229 / 28,253 / 29,630 字符——即每次 `sike_read_turn` 的完整回执。
这些回执 **一旦产生就留在上下文里，回合内不会被移除**，于是越读越贵：
第 1 步 13 万 → 第 16 步 20 万。

### 2.2 旧流程的具体浪费

turn 3 的 19 步序列（实测）：

```
ready_draft(v6) → read_turn → prepare_turn → put_draft
→ read_turn → run_module(parallel) → check_draft → patch_draft
→ run_module(parallel) → check_draft → read_turn
→ patch_draft → read_turn → check_draft → run_module(parallel) → check_draft(v6)
```

- **平行模块重跑 4 次**：改一次正文就让平行事件收据失效，重跑又推进草稿版本，
  版本一变审稿收据又失效 → 再 check → 再报 revise → 再 patch。这就是审计 §3.4 描述的棘轮。
- **`sike_read_turn` 调了 3 次**（step 2 / 5 / 11）。
- **结算被拆成 5 个独立后台任务、14 次请求**，其中 MVU 结算在 08:32 / 08:36 / 08:39
  连续尝试 3 次（每次第一步都不调用工具，先空跑 28–48 秒）。
- **平行模块用持久后台会话反复重跑**，会话消息数 3 → 5 → 7 → 10 → 12 → 15 → 17 持续累积。

## 3. 重构落地核对（源码 + 部署）

以下均在源码中存在，且 `data/harness/apps/dsh-tavern` 部署副本与源码 sha256 全等：

| 重构项 | 落地情况 | 证据 |
| --- | --- | --- |
| 前台流程合并 | 已落地 | `dream-sike-tool-phase.js` 已无 module 阶段；阶段为 reading → draft → (revision)，`put_draft` 由宿主同次自动检查+确认 |
| `run_module` 退出主流程 | 已落地 | 工具描述明写「旧版独立草稿模块兼容工具。当前梦境思客流程不调用」 |
| 合并结算 | 已落地 | `SETTLEMENT_SUBMIT_TOOL_NAME = 'settlement_submit'`，「本轮只允许一次 settlement_submit；失败时停止本轮，不再发起自动修正请求」 |
| 合并附加 | 已落地 | `sike_submit_followup` 一次提交全部已选模块 |
| 调用预算 | 已落地 | `dream-sike-execution-policy.js`：query 1–2、revision 0–2 |
| 变量游标绑定 | 已落地 | 提交 `cc778d49` |
| 省略 brief 不再多请求 | 已落地 | `prepareDreamSikeWriting` 缺省时记 `briefOmitted`，`assertDreamSikePreparation` 接受 inline 模式 |

**按当前源码，一个普通回合的请求数应为 2–3 次**（reading 1 次 + draft 1 次，
必要时 1 次修订），而不是旧流程的 19–42 次。这是本次重构最大的价值。

### 3.1 但是：从未验证

- 重构部署时间：今天 12:01–15:41。
- 最近一次真实回合：今天 08:19–08:55。
- 08:55 之后没有任何模型请求产生（应用今天下午启动过 3 次，但没有跑出回合）。

所以：**36 分钟那个数字是旧流程的成绩，不能用来评价新设计；新设计也还没有任何实测数据。**

## 4. 尚未解决的缺陷（按影响排序）

### 4.1 回合内上下文没有上限（最高）

`agent.cordis.yml` 的压缩组配置是：

- `compaction-basic`：`thresholdRatio: 0.5` —— 按**模型窗口比例**触发。窗口大的模型
  （这次峰值 20 万仍能发出）永远不会触发压缩。
- `tool-result-pruner`：`thresholdChars: 8192, headChars: 4096, tailChars: 1024`。

实测后果：在 `chat-mv3hd5o2-bd9hdf`（救赎之理）的请求体里，**稳定出现 7 处**
`[... tool result middle pruned ...]`，被裁的正是 `sike_read_turn` 回执，
原 ~20,000–29,000 字符被压成 **5,601–5,636 字符**。

也就是说：**作者规则页的中间段（`presetRules` 所在位置）被静默删掉了。**

需要说明的是，作者规则本身还有另一条通道（`back` 阶段按步注入），所以这不是规则彻底丢失；
但它造成两个后果：
1. `sike_read_turn` 这次读取很大程度是白读的，模型看不到规则正文 → 倾向于再读一次 → 每次再读约 17 万 token。
2. 同时 `AUTHOR_RULE_READ_CHARS = 20000` 与裁剪阈值 8192 **直接冲突**：
   设计承诺「摘要不是规则原文」，配置却保证规则页永远无法完整送达。

### 4.2 正文不出现在聊天（次高，且最影响观感）

审计 §3.5 指出的问题**没有修**：正文写在 `sike_put_draft.text` 的工具参数里，
主聊天在提交前只显示阶段状态，客户端没有订阅 `agent/assistant-stream` 做增量预览。

所以即使新流程只要 2–3 次请求，玩家仍然要**盯着「生成中」等到正文整篇出现**。
「不如以前酒馆」的体感，很大一部分来自这里，而不是请求数。

### 4.3 没有绝对 token / 时间预算

设计文档 §6 提出的「45 秒软提醒 / 120 秒安全暂停」以及绝对 token 试验线，
在源码中没有对应实现。目前只有请求次数上限，没有耗时与上下文上限。

### 4.4 结算与附加仍是独立请求

合并后它们各占 1 次请求，且结算没有模型请求硬上限。
旧流程的结算重试 3 次的问题，新代码声称「失败即停」，但**未验证**。

### 4.5 后台会话持续膨胀

`dream-draft-module` 复用持久后台会话，消息数在同一天内从 3 涨到 17。
设计文档 §8.6 要求「下一任务只取得必要的状态摘要」，尚未落实。

## 5. 给用户的两条路径

### 路径 A：要「以前酒馆的手感」——切换回复方式

`原版酒馆 · 单次回复` 已经实现（提交 `d9fc3c8e`），就在「本局设置 → 预设 → 回复方式（本局）」。
它按原 `prompt_order` 展开作者提示、卡片、世界书、历史、宏与正则，**主生成只请求一次**，
不发起草稿检查、修订、状态规划、记忆整理、候选、后续模块或压缩模型任务；
原正则和 HTML 负责展示，官方 MVU 用同次回复的 `UpdateVariable` 本地事务处理。

这就是「之前的酒馆效果」本身。**Agent 模式在结构上不可能比它快**，因为 Agent 模式本来
就多做了检索、审阅、结算与附加。如果目标是手感，直接用这条路。

### 路径 B：要 Agent 的质量——按下面顺序补齐

1. **对齐规则页与裁剪阈值**（一次性、低风险）。已在本轮改好（见 §6）。
2. **接入正文流式预览**（收益最大）。复用原生 `agent/assistant-stream`，
   白名单提取当前 `sike_put_draft` 的 `text` 参数增量，100–200 ms 合并刷新，
   在主聊天固定位置显示「正文生成中 · 未提交」。这是把「2–3 次请求」变成
   「几秒就能读」的关键，也是与酒馆手感差距的主要来源。
3. **加绝对预算**：本回合总工作上下文软阈值（建议先按 64k 试）+ 回合耗时软提醒，
   达到边界时保留草稿并给出继续/提交/取消三个选项。
4. **收敛回合内工具回执**：同一回合内重复的 `sike_read_turn` 只保留最新一份，
   旧回执在组装下一请求时替换为引用摘要（审计记录仍完整保留）。
5. **后台会话瘦身**：每次结算/附加任务只注入必要的状态摘要与引用。

## 6. 本轮已做的修改

| 文件 | 改动 | 理由 |
| --- | --- | --- |
| `presets/dream-sike-dsh/agent.cordis.yml` | `tool-result-pruner` 阈值 8192/4096/1024 → 34000/31000/2500 | 让完整的作者规则页（最大约 29,600 字符）不再被裁掉中间段；同时仍会裁剪异常巨大的回执 |
| `presets/hushen-dsh/agent.cordis.yml` | 同上 | 同一问题，狐神抚的规则页约 9,640 字符同样会被裁 |

这是配置层改动，不改变任何作者规则、供应商或角色卡，回滚只需还原这两个文件。
**但它必须在一次真实回合里验证**：确认请求体中不再出现 `middle pruned` 裁掉规则页，
并对比「首见正文时间 / 总请求数 / 工具错误数」。

## 7. 验收标准（重要：现有审计没有把速度列为门槛）

下一次真实回合必须同时记录以下六项，缺一项就不算验证通过：

1. 首个可读正文出现的时间（毫秒）
2. 正式正文提交时间
3. 正文前模型请求数（目标：普通卡 ≤ 3）
4. 完整往返请求数（目标：3–6）
5. 实际输入 token 峰值（目标：不再触达 20 万）
6. 工具错误数与错误分类

同一张卡、同一输入、同一作者选项下做对照，不能只用「工具调用成功」当作通过。
