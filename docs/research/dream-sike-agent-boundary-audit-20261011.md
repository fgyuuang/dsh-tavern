## 程序真正强制的流程

写作模式且启用链条时：read_turn 形成与局、回合、操作、分支、剧情版本及规则摘要绑定的读取凭据；prepare_turn 要求六项8–400字符的简短事实或执行约束；put_draft 才能建立唯一草稿。check_draft 要求六维审稿结果，ready_draft 校验当前草稿版本、准备、契约与检查结果；宿主提交确认正文一次。缺确认时宿主继续引导工具处理，超过12个模型步骤保留失败状态与草稿。

六维为人物、信息差、文风、连续性、玩家选择和格式。程序验证 pass/revise 结构、依据长度、非空泛用语及已知私有协议标记；有 revise 或确定性错误则不能确认。确定性检查覆盖部分区块数量、标签配对、场景日期时间地点、平行事件行格式、最低字数与少量禁词等，不能称为完整 XML/schema 或全部作者禁词验证。

局部补丁必须版本一致且 FIND 唯一，确认后禁止修改；正文提交后后台依据最终正文结算。当前实现是最多两次有效 `patch_draft` 调用，不是每轮可包含多个补丁的“两轮完整审稿”。聊天和总结模式豁免剧情准备/六维审稿等要求，仍使用唯一草稿及原生提交检查。

## 主要发现与改进优先级

1. **规则覆盖未形成硬门槛。** coverage 可选；它校验引用确实已提供，不校验所有关键规则已完整读完。ruleReadRanges 记录读取区间，却没有必须覆盖 writer、当前 chain、style、narrator、charAnalysis 的断言。建议针对所选任务定义必要完整材料的覆盖门槛，避免无关全量读取。
2. **四章只有软遵从。** 六项 brief 不能证明检设定、逐项写规和三条事件链均被认真完成。建议记录简短可观察的计划结果、选用资料和行动边界；不要要求公开完整内部推理。
3. **审稿为同一 Agent 自评。** 8–500字符依据可以看似具体但不匹配正文，程序没有逐条验证。建议文风/关键角色约束要求引用短正文片段及作者规则 ID，复杂场景可引入独立审阅，并以玩家体验评估文学质量。
4. **修订次数命名与粒度不一致。** 两个独立局部问题即可能用尽上限；建议明确按补丁计数或实现一轮多个原子补丁，保持唯一定位与版本规则。
5. **协议标记检查不是语义识别。** `hasPrivateWritingProtocol` 匹配 think 等标签/围栏，不能保证自然语言中没有冗长推理，也可能误判角色引用的同名标签。
6. **不要将原 persona 的所有文字损失混称“迁移成功”。** 创作方法、接口协议适配与限制声明处理应在原文对照里分别标明，才能判断使用体验变化来自何处。
