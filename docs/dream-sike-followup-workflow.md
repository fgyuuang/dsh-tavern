# 梦境思客：正文与后续互动分阶段调用

## 使用顺序

1. 前台 Agent 按作者文风和人物规则准备、起草、审稿，提交一次正式正文。
2. 原有持久后台 Agent 根据最终正文完成变量、姿势及启用的记忆任务。
3. 结算提交完成后，同一后台 Agent 用另一次任务调用生成已选的“思客大调查”和行动选项。
4. 独立“后续互动”面板先显示剧情共创，再显示行动选项。可收起，失败可单独重试。

仅启用对应原作者模块时才有第三步。DSH 原版候选流程、大总结与聊天模式沿用现有行为。场景和已选平行剧情仍属正式正文；后续互动不推进剧情、不触发变量结算、不成为第二条正式消息。更新从下一回合采用新流程，历史原文保持原样。

## 作者规则与原生边界

契约版本 8 按原 identifier 将两种行动选项和思客大调查移至 `deferredFollowup`。保存完整原文、选项名称与摘要；不修改原预设资源。前台请求与规则分页不再要求同次生成这些区块，审稿拒绝将 `dream_option` 或 `dream_big_discuss` 塞回正文。配置页面按“后续互动”阶段管理原开关。

后续请求使用最终正文、结算后变量、人物状态、玩家输入和选定模块的完整作者原文。`sike_submit_followup` 只收可显示的互动文本，校验选项及问题格式，拒绝正文、变量协议或私有推理。原作者正则与 HTML 按钮继续用于展示。Skills 和原生角色说明同步该阶段边界。

工具进入后台固定目录，由运行时按当前任务授权执行；其他任务不能调用后续提交。共享后台会话、历史召回、世界书读取和原生压缩继续复用现有实现。第三步有独立工具调用预算，不占前台十二步；不会因面板收起停止执行。

## 持久化与一致性

本局最新回合的派生产物保存于 `dreamSikeFollowup`，包含分支、回合、正文和规则摘要、状态与显示投影。模型任务由原有 Background Task Coordinator 绑定剧情 revision 及持久后台会话；提交前再次核对正文、变量、预设和脚本生命周期。迟到或过期结果不能覆盖新回合。

`queued → running → done/failed` 在游戏存储中保存；重启只恢复已经排队或运行中的任务，不为旧存档补发调用。并发唤醒合并为一次任务，成功后不重复执行；失败保留正文与变量，可按当前回合 key/turn 独立重试。后续模块准备失败不会阻止变量结算。

正文新提交或编辑清理旧产物；回退及替代生成失败恢复对应检查点的产物，并重新绑定恢复分支。轻量会话读取也包含该字段，避免变量刷新使面板消失。iframe 采用独立 partIndex 命名空间，不挂载正式消息 scriptLayer；过期回合的按钮拒绝提交。
