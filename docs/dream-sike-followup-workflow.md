# 梦境思客：正文与后续互动分阶段调用

## 使用顺序

1. 前台 Agent 按本局档位进行 1–2 次正文前查询；一次提交正文和审阅。需要修订时，最多使用设置中的 0–2 次修订请求，宿主只提交一次最终正文。
2. 原有持久后台 Agent 每次结算任务尝试通过一次组合工具提交变量、姿势及启用的记忆；恢复会另开任务并单独记账，结算全过程仍按实际模型请求次数统计。
3. 结算完成后，同一后台 Agent 用一个聚合任务与一次工具提交生成所有已选附加模块，包括平行事件、思客大调查、说书共创、行动选项和小摘要。
4. 各附加模块在独立“后续互动”面板按现有顺序显示。可收起，失败可单独重试。

仅启用对应原作者模块时才生成相应附加内容。DSH 原版候选流程、大总结与聊天模式沿用现有行为。平行事件是结算后的派生展示，不属于正式正文，不改变本轮权威事实、变量或记忆；后续互动不触发第二次结算，也不成为第二条正式消息。更新从下一回合采用新流程，历史原文保持原样。

## 作者规则与原生边界

契约按原 identifier 将平行事件、行动选项、思客大调查、说书共创与小摘要移至 `deferredFollowup`。保存完整原文、选项名称与摘要；不修改原预设资源。前台请求与规则分页不再要求生成这些区块，宿主拒绝将它们塞回正文。配置页面按“后续互动”阶段管理原开关。

单次后续请求使用最终正文、结算后变量、人物状态、玩家输入和所有已选模块的完整作者原文。`sike_submit_followup` 只收可显示的互动文本，校验选项及问题格式，拒绝正文、变量协议或私有推理。原作者正则与 HTML 按钮继续用于展示。Skills 和原生角色说明同步该阶段边界。

工具进入后台固定目录，由运行时按当前任务授权执行；其他任务不能调用后续提交。共享后台会话、历史召回、世界书读取和原生压缩继续复用现有实现。正文前查询与正文修订/恢复请求可按本局档位调整；状态结算只接受一次组合提交，后续展示限一次模型请求。结算没有模型请求硬上限，人物设计等工具流程可能增加请求。面板收起不会停止执行。

## 持久化与一致性

本局最新回合的派生产物保存于 `dreamSikeFollowup`，包含分支、回合、正文和规则摘要、状态与显示投影。模型任务由原有 Background Task Coordinator 绑定剧情 revision 及持久后台会话；提交前再次核对正文、变量、预设和脚本生命周期。迟到或过期结果不能覆盖新回合。

`queued → running → done/failed` 在游戏存储中保存；重启只恢复已经排队或运行中的任务，不为旧存档补发调用。并发唤醒合并为一次任务，成功后不重复执行；失败保留正文与变量，可按当前回合 key/turn 独立重试。后续模块准备失败不会阻止变量结算。

正文新提交或编辑清理旧产物；回退及替代生成失败恢复对应检查点的产物，并重新绑定恢复分支。轻量会话读取也包含该字段，避免变量刷新使面板消失。iframe 采用独立 partIndex 命名空间，不挂载正式消息 scriptLayer；过期回合的按钮拒绝提交。
