## Token 的口径

DSH 的标准化 `TokenUsage` 使用互斥计数：

```text
完整输入 = inputTokens + cacheReadTokens + cacheWriteTokens
缓存读取率 = cacheReadTokens / 完整输入
```

这里的 `inputTokens` 是未缓存输入，不是 OpenAI/DeepSeek 原始响应中的整体 prompt tokens。原始提供方字段必须经 DSH adapter 标准化，不能直接混用。缺失 usage 表示未知，缺失缓存计数不伪造为 0。存在精确 `totalTokens` 与 `outputTokens` 时，用二者之差确定整体输入。

本次样本未报告缓存写入计数；它们的精确整体输入由 `totalTokens - outputTokens` 验证，与未缓存输入加缓存读取相符。真实缓存使用率取自提供方回报；字符前缀相似度仅解释结构，不能替代缓存使用率。

## 当前上下文管理

1. **稳定资料**：角色卡、用户长期偏好、卡片系统提示和常驻世界书形成持久快照；原生 system assembly 是模型可见固定资料的唯一装配入口。
2. **动态资料**：本轮行动、动态世界书、变量反馈和记忆索引主要作为回合消息追加；部分世界书模板会在请求投影阶段按当前状态重新展开。
3. **预设**：前置作者规则进入 system，后置规则在请求末尾投影。每步重算边界但不应把所有历史边界累加；中段规则按回合进入历史。动态宏可能改变前置内容。
4. **Agent 执行历史**：工具调用与结果、准备、草稿、审稿、修订以及提供方要求的 reasoning replay 保留在原生 Surface；正式故事记录与工作过程分别保存。
5. **后台**：稳定工具目录与 system prefix 保持共享；各任务的当前变量、最终正文、协议作为新的 user 任务消息追加。世界书筛选、状态结算、候选和后续任务由任务权限约束。
6. **长期记忆**：正文确认后，后台维护分支绑定的记忆文档；前台先接收索引，需要时通过工具检索和读取。
7. **压缩**：前后台均复用 DSH 原生压缩；剧情压缩还支持手动、轮数、百分比策略。默认保留近期 10 轮原文，并限制保留预算为窗口的 25%；旧历史摘要后能通过文档、变量与世界书恢复资料。

原生 token meter 已使用真实 usage 校准历史基线，再计入 Surface 增减；不是始终只按字符数除以 4。尚无样本或切换路由时会回到估算。中文新追加内容、巨大工具结果和模型路由变更仍需要真实 usage 对照，不能仅凭静态估算认为窗口安全。

## 发现与最小优化

### 1. 规则分页重复携带整个回合材料

`lib/tools/dream-sike.js` 的 `turnReport` 每次返回玩家行动、近期历史、世界书片段、变量片段、作者契约、完整 preparation、草稿以及规则页。

本局有 9 次 `sike_read_turn`。8 个可解析的投影结果累计携带非规则数据 103,506 字符。3 次 `ruleOffset > 0` 请求的非规则部分分别为 12,250、8,250、12,531 字符，共 33,031 字符；其中真正行动/历史/世界书/状态仅 1,510、3,204、4,867 字符，额外的大头是重复契约和逐页增长的 preparation 引用。

草稿续读也默认再次返回规则第一页约 9,178 字符；应把规则分页和草稿读取分开选择。一个历史结果的投影文本无法按 JSON 解析，本次将其排除数值拆分，不能推断它的内部字段长度。

**建议**：首次读取完整回合材料；同一 operation、分支、storyRevision、变量摘要和契约摘要未变时，规则续页只返回规则、已读取版本索引及变更标识。显式 `full` 允许重新获取完整材料；压缩后或材料变更后自动重新提供全文。不能仅按工具名字去重，也不能忽略修改后的草稿和变量。

### 2. 原生执行历史是主要增长来源

最新前台请求的规范结构约 346,039 字符；按块计数，text 73,069、历史 reasoning 158,935、工具参数约 29,826、工具结果约 62,521 字符。这些数字是字符统计，不是 token 估算；工具结果 JSON 的转义与结构有额外开销。

**建议**：优先缩小新返回的工具资料；在已完成回合边界，由原生压缩/Surface 替换将工作过程变成简短完成记录，并保留正式正文、准备约束、修改摘要、资料引用及原始事件。当前回合工具配对、DeepSeek 同轮思考回传、分支回退和压缩恢复必须完整保留。不能直接删除全部 reasoning 或孤立工具消息。

### 3. 后台重复规则与状态仍可分层

`lib/domain/mvu-background-settlement.js` 将变量 schema、卡片更新规则、当前变量逐项放入 task context；独立后续任务还再次放入最终正文与完整变量。它们没有被放进动态 system，现有设计有稳定前缀优势，但跨任务仍重复材料。

**建议**：为确定性 schema/更新规则建立版本化引用与请求投影去重；变化后的状态快照必须明确提供。后续模块按所需变量读取，不能无依据假设共享后台历史已经包含结算后的完整状态。

### 4. 将可分离的作者模块按阶段组织

作者的平行事件、构思、摘要、共创及行动选项各有不同用途。先判定本轮启用项，再选择正文前准备、正文内内容或结算后输出；各任务只读取相关作者规则，不让所有模块争夺一次正文输出。保留完整作者原文来源、选择开关和协议校验，不以新写摘要替代原规则。

### 5. 增加可持续的真实计量

原 `model-request-log` 仅保存响应文本、finish、error，没有 usage；真实计数必须另读原生 Session，不利于前端诊断。本次新增流 usage 白名单采集和只返回数字的审计接口，后续回合可持续量化。

默认审计读取至多 100 个最近请求的结果 sidecar，不加载正文。显式前缀审计仅加载至多 8 个保留请求，按 Session、提供方、模型分别比较，输出 SHA-256、字符总数和公共前缀长度。规范角色/内容/tools/system 的 JSON 不是提供方线缆序列化，LCP 不宣称实际缓存命中。

未报告 usage 的旧请求继续标记未知；不回填虚构计数，也不根据耗时倒推缓存率。此次真实原生 usage 审计是有限样本，不能推广为所有卡片、所有模型的保证。
